# 数据库慢查询处理 Runbook

## 适用场景

当 order-service 的订单列表、订单详情或订单查询接口延迟明显升高，并且日志、指标或链路追踪中出现 database slow query、数据库慢查询、slow query、full table scan、SQL 执行耗时过高等信号时，适用本 Runbook。

典型表现包括：接口 P95/P99 延迟升高、`db.query.latency.p95` 超过阈值、慢查询数量增加、数据库连接池等待增多，或者 Trace 中 mysql / database span 耗时过高。

## 常见原因

1. 查询条件缺少合适索引，导致 full table scan。
2. 订单列表使用深分页，offset 过大导致扫描行数过多。
3. SQL 返回字段过多，或者 join 关系过重。
4. 高峰期数据库连接池耗尽，请求排队等待连接。
5. Redis 缓存失效后，大量请求回源数据库，引发数据库慢查询。

## 排查步骤

1. 查看 order-service 日志，确认是否出现 slow query、SQL 执行耗时过高、full table scan 或索引缺失提示。
2. 查看 `db.query.latency.p95`、`db.query.latency.p99` 和 `db.slow.query.count`，确认数据库查询延迟是否持续升高。
3. 查看链路追踪中 mysql / database span 的耗时、状态和错误信息，确认慢点是否集中在数据库查询节点。
4. 使用 explain 分析慢 SQL，检查是否命中索引、扫描行数、排序方式和回表情况。
5. 检查最近是否发布了新的查询条件、排序逻辑、分页策略或索引变更。

## 修复建议

1. 为高频查询条件补充合适的单列索引或组合索引，例如 user_id + created_at。
2. 将深分页改为基于游标或最后一条记录的分页方式。
3. 限制查询返回字段，避免不必要的大字段和复杂 join。
4. 对热点订单查询增加缓存，并设置合理过期时间和缓存击穿保护。
5. 如果需要新增大表索引，应评估锁表风险，在低峰期或使用在线 DDL 方式执行。

## 风险提示

不要在高峰期直接对大表执行高风险索引变更。索引创建可能占用大量 IO、锁资源或复制延迟，导致数据库进一步抖动。应先评估表大小、数据库版本、在线 DDL 能力和回滚方案。
