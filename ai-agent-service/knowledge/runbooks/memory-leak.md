# 内存泄漏与持续增长处理 Runbook

## 适用场景

当服务内存使用量持续增长、频繁 Full GC、容器被系统终止或实例周期性重启时，适用本 Runbook。常见日志关键词包括 `java.lang.OutOfMemoryError`、`Java heap space`、`GC overhead limit exceeded`、`OOMKilled`、`Cannot allocate memory`、`内存不足`；常见指标包括 `jvm_memory_used_bytes`、`jvm_memory_max_bytes`、`process_resident_memory_bytes`、`container_memory_working_set_bytes`、GC pause、对象分配速率和容器重启次数；Trace 中可能表现为同类请求随运行时间逐渐变慢、GC 暂停期间多个 span 同时延迟或 allocation-heavy endpoint 反复出现。

内存占用高并不等同于内存泄漏。更明确的证据是多次 GC 后基线仍持续上升、相同对象数量或 retained size 持续增长，并且增长趋势与流量回落无关。Trace 只能帮助定位触发路径，不能单独证明泄漏。

## 常见原因

1. 无界缓存、集合、去重表或本地会话持续保留对象。
2. `ThreadLocal`、监听器、回调或类加载器引用没有释放。
3. 消息队列、线程池或异步任务积压，待处理对象长期驻留内存。
4. 大对象、文件或响应体一次性读入内存，导致分配速率和 GC 压力过高。
5. 数据库连接、文件句柄或直接内存等本地资源泄漏。
6. 容器 memory limit 与 JVM 堆、直接内存和线程栈总量不匹配。

## 排查步骤

1. 查看至少一个完整业务周期的堆、RSS、GC、请求量和实例重启趋势，区分稳定高水位、突发大对象和持续增长。
2. 检查容器事件和退出码，确认是应用抛出 `OutOfMemoryError`，还是容器超过 memory limit 后被标记为 `OOMKilled`。
3. 对 Java 服务比较 GC 前后的 old generation 使用量、Full GC 次数和停顿时间。Full GC 后基线持续抬升是重点信号。
4. 在获得授权且磁盘空间充足时，采集类直方图、JFR 或 heap dump，比较不同时间点对象数量和 retained size，定位持续增长的对象及引用链。
5. 按 endpoint、消息类型或任务类型检查 Trace，寻找与内存增长时间相关的大响应、批量加载、重试或长生命周期任务。
6. 对比最近发布和配置变更，重点检查缓存上限、队列容量、批大小、并发数、文件处理和依赖版本。

## 处理建议

1. 内存即将耗尽时可分批重启受影响实例作为临时缓解，同时保持足够健康副本并保留诊断证据。
2. 为缓存、集合、队列和批处理增加容量上限、过期策略与背压，修复未释放的引用或资源。
3. 对大文件和大结果集改用流式处理、分页或分块读取，限制单次请求可分配的数据量。
4. 确认业务内存需求合理后，再协调调整 JVM 堆和容器 memory limit，并为堆外内存、线程栈和运行时预留空间。
5. 修复后执行持续压测或长时间回归，验证 GC 后内存基线稳定、对象数量不再单调增长且重启次数归零。

## 风险提示

Heap dump 可能包含令牌、用户数据、SQL 参数等敏感信息，并可能占用大量磁盘和短暂停顿应用。不得在磁盘空间不足时直接生成，也不得上传到未授权位置。批量重启只能暂时释放内存，可能放大流量抖动；盲目扩大堆或 memory limit 可能延迟 OOM 并增加 GC 停顿，不能替代根因修复。
