# 项目复盘与 Codex 协作方法

更新时间：2026-08-02。

这份文档服务两个目的：判断项目有没有偏离“AI 应用开发面试亮点项目”的目标，
以及说明后续如何用主 Agent 和子 Agent 高质量维护项目。

## 结论

项目当前没有跑偏，已经从“能演示的 AI Demo”升级为“可验证的 AI 后端工程项目”。
主线仍然清楚：

```text
Java 后端工程能力
  + 受控 AI Agent / RAG
  + 稳定性、审计、可观测性和评测
  = AI 应用开发岗位的作品级证据
```

它适合证明任务编排、工具调用、RAG、AI 安全边界、评测和工程交付能力；不适合
包装成真实生产 SRE 平台，也不应为了追热点追加与诊断主线无关的技术。

## 本轮校准前的问题

| 问题 | 对面试价值的影响 | 本轮处理 |
| --- | --- | --- |
| 只有确定性工作流 | 易被质疑不是真实 Tool Calling | 增加可插拔 OpenAI-compatible 模型循环，默认模式不变 |
| 只有 Dense 检索和 3 份 Runbook | RAG 深度不足，指标缺少干扰项 | 增加 BM25 + RRF、9 份 Runbook、24 条排名评测 |
| AI 审计没有模型/Prompt/Token | 无法解释模型版本、成本和降级 | 贯通数据库、DTO、指标和前端元数据 |
| 工具只做基础白名单 | 模型可能请求跨服务或跨 Trace 数据 | Python 与 Spring 双层收敛权限 |
| 缺少统一 CI/smoke 入口 | README 中的“可用”难复现 | 增加 GitHub Actions、`verify.sh` 和 `smoke_http.py` |
| Docker 冷构建缓存不可靠 | 一键启动在弱网下失败 | 改为实际 package 产出层 + Maven 仓库加速缓存 |
| 文档仍描述“未实现外部 LLM” | 代码和简历口径不一致 | 重写 README、架构、路线、评测和面试材料 |

## 当前证据矩阵

| 能力 | 代码证据 | 验收证据 | 正确表述 |
| --- | --- | --- | --- |
| 异步诊断与 SSE | Spring task/executor/emitter/recovery | 三场景整栈 smoke + 启动对账单测 | 页面可恢复状态，单实例重启可终止并对账遗留任务 |
| Tool Gateway | 白名单、归属、服务/Trace 校验 | Java 单测 + 工具审计 | 构建受控只读工具执行边界 |
| 确定性诊断 | Python diagnosis workflow | Docker `3/3 PASS` | 无密钥、可重复的基线诊断器 |
| 模型 Tool Calling | Agent runtime + compatible client | 模拟模型单测 | 实现可插拔真实模型协议，尚未现场验收供应商 |
| 混合 RAG | Chroma、BM25、RRF | 24 条查询三指标 1.00 | 在小型回归集上全部首位命中 |
| 稳定性 | Redis、Resilience4j、fallback | 单测与 smoke | 具备缓存、限流、去重、熔断和显式降级 |
| 可观测性 | Metrics、OTel、Tempo、Grafana | Compose 运行时验证 | 贯通任务、AI 和工具调用链路 |
| 前端交付 | React/Nginx | 1440 与 390 真实浏览器验收 | 支持桌面和移动端演示，无横向溢出 |

## 重要架构取舍

### 保留确定性默认模式

作品展示不能依赖面试现场的网络、余额或某个模型版本。确定性模式承担稳定基线，
LLM 模式承担真实 Agent 协议展示；二者复用同一工具与报告合同。这比把所有能力
绑定在一个外部模型上更容易回归，也更容易解释降级策略。

### 单 Agent 产品，主子 Agent 开发

产品运行时保持单 Agent，因为当前诊断任务不需要多个自治角色。开发过程中可以用
主 Agent 和子 Agent 并行处理边界清晰的工作，但那是研发方式，不是产品功能。
两者必须在简历中严格区分。

### 先做工具权限，再谈 Agent 自主性

模型自主选择工具只有在服务、Trace、参数、步数、结果长度和审计边界都明确时才有
工程意义。Prompt 是辅助约束，真正权限由代码和 Tool Gateway 决定。

### 用评测门槛替代“感觉不错”

诊断评测验证完整业务闭环，RAG 评测验证排名，两者分别失败退出。当前数据集很小，
所以数字只能证明回归稳定，不能推导生产准确率。

## 主 Agent 职责

主 Agent 是项目总控，不能把以下事项委托后直接照单全收：

- 冻结范围、非目标和验收标准。
- 维护 Java/Python/前端之间的请求、响应和审计合同。
- 决定数据库、权限、安全和可观测性边界。
- 处理跨模块集成、迁移兼容和最终冲突。
- 审查所有子 Agent 变更和测试证据。
- 运行统一回归、整栈 smoke 和浏览器验收。
- 维护 README、架构、复盘和简历的事实一致性。

主 Agent 的核心产出不是“写了最多代码”，而是所有模块最终组成一个可验证系统。

## 适合交给子 Agent 的任务

子任务应满足三个条件：边界清晰、写入文件集合互不重叠、主线可以同时推进。

本轮采用的拆分：

| 子任务 | 写入范围 | 为什么适合并行 |
| --- | --- | --- |
| CI 与 smoke 脚本 | `.github/`、`scripts/` | 和业务合同弱耦合，可独立验证 |
| 混合 RAG 实现 | `app/rag/`、RAG 测试与评测脚本 | 接口保持兼容，模块边界明确 |
| 六份长尾 Runbook | `knowledge/runbooks/` | 内容任务，不修改运行时代码 |

不建议委托：

- 同时修改 Java 与 Python 报告合同。
- Agent 权限策略和 fallback 语义。
- 数据库兼容、最终 Docker 集成和整栈验收。
- README、简历和最终“项目是否完成”的判断。

## 子 Agent 任务合同

每次委托应包含：

```text
目标：一个可验证的具体结果。
允许修改：精确到目录或文件。
禁止修改：合同、文档或其他 Agent 的写入范围。
兼容要求：必须保持的函数、API 或字段。
验收命令：子 Agent 自己应运行的测试。
返回内容：修改文件、测试结果、限制和需要主 Agent 集成的事项。
```

示例：

```text
实现 Runbook hybrid search。
只修改 ai-agent-service/app/rag、对应 Python 测试和 RAG 评测文件。
保持 search_runbooks(query, n_results) 的调用方式兼容。
使用 Dense + BM25 + RRF，结果需暴露检索模式和排名。
运行相关 unittest，返回文件清单、测试数和已知限制。
不要修改 README、Java、前端或 Docker Compose。
```

## Codex 高质量工作流

### 1. 先读事实，再写计划

先读 README、`docs/`、关键合同、Git 状态和已有测试。计划应由现有系统推导，
不能仅按用户的一句话想象代码结构。

### 2. 把目标写成可验收事实

不要写“增强 RAG”，应写：

```text
9 份 Runbook；24 条查询；输出 Hit@1/Hit@3/MRR；低于门槛退出 1。
```

不要写“接入大模型”，应写：

```text
兼容 /chat/completions；模型能调用五类只读工具；输出通过合同校验；
失败显示 LLM_FALLBACK；没有密钥时默认路径仍可运行。
```

### 3. 先冻结合同，再并行实现

主 Agent 先决定模式枚举、报告字段、权限规则和测试门槛。子 Agent 只在这些边界内
工作，避免多个 Agent 同时发明不同接口。

### 4. 子 Agent 返回后必须复核

主 Agent 应阅读 diff 和关键代码，而不是只看“已完成”。检查：

- 是否修改了超出范围的文件。
- 是否保持兼容合同。
- 测试是否真正覆盖新行为。
- 是否把模拟能力写成真实能力。
- 是否引入高基数指标、密钥泄露或越权入口。

### 5. 分层验证

```text
模块单测
  -> ./scripts/verify.sh
  -> docker compose up -d
  -> ./scripts/smoke_http.py
  -> RAG 门槛评测
  -> Playwright 桌面/手机验收
  -> git diff --check 和文档事实检查
```

每一层解决不同风险。单元测试通过不等于 Docker 能构建，容器健康也不等于业务闭环
通过，页面能打开也不等于移动端没有溢出。

### 6. 最后更新文档

文档中的数量、状态和延迟只引用当前运行结果。没有真实密钥、真实数据源或生产环境
证据时，使用“已实现并模拟测试”“待现场验收”，不要使用“已上线”“生产级”。

## 不再盲目增加的内容

当前不建议为了简历继续堆叠：

- 多 Agent 产品运行时。
- Fine-tuning。
- Kubernetes 和服务网格。
- 自研向量数据库或自研模型网关。
- 仅为追热点而接入 MCP。

这些能力只有在目标岗位明确要求、并且能形成新的可验证业务价值时才进入范围。
否则会稀释 Java 后端、受控 Agent、RAG、评测和可观测性这条主线。

## 后续优先级

项目已经达到可投递和可演示标准。继续优化时按以下顺序：

### P0：真实模型现场验收

- 选择一个支持工具调用的 OpenAI-compatible 模型。
- 按 [真实模型验收清单](07-llm-agent-and-evaluation.md#真实模型验收清单) 记录结果。
- 增加成功率、P50/P95、Token 和单任务成本，不只记录一次成功截图。

### P1：真实数据适配器与权限

- 为日志、指标、Trace 和发布记录定义 Adapter 接口。
- 至少接一个真实只读数据源或本地开源系统。
- 增加身份、租户、RBAC、脱敏和人工审批边界。

### P1：扩大评测可信度

- 增加同义改写、拼写错误、证据缺失和相似故障对抗样本。
- 区分检索指标、报告事实一致性和端到端任务成功率。
- 保存版本化基线，避免只展示当前最好结果。

### P2：按岗位定向增强

- 岗位强调 MCP 时，再把现有工具合同映射成 MCP Server。
- 岗位强调平台工程时，再增加消息队列、任务恢复和水平扩展实验。
- 岗位强调模型应用时，再评估 reranker、上下文压缩或多模型路由。

## 面试前停止线

以下条件都满足后，应停止加功能，转向讲解和投递：

- [x] 默认模式无密钥可启动、可演示。
- [x] Java、Python、前端和 Compose 验证通过。
- [x] 三场景诊断和 RAG 排名有可复核结果。
- [x] 工具权限、审计、降级和已知限制能讲清楚。
- [x] README、架构和简历口径一致。
- [ ] 对目标岗位需要时，补一份真实模型验收记录。

最后一项是针对岗位的增强，不阻止当前项目作为简历作品使用。
