## 推荐项目名称

```text
OpsMind AI：证据驱动的微服务故障诊断平台
```

## 简历四条版

- 基于 Spring Boot 3 / Java 21 构建 AI 诊断控制面，将耗时诊断抽象为
  `PENDING/RUNNING/SUCCESS/FAILED` 异步任务，通过 SSE 推送过程事件；使用 MySQL
  保存可靠状态，Redis 实现任务快照、10 分钟结果复用、固定窗口限流和分布式去重。
- 设计六工具 Tool Gateway，统一执行日志、指标、Trace、Runbook、发布记录和复盘，
  实现任务/故障归属、服务与 Trace 范围校验、参数收敛和成功/失败审计；Python 服务
  不直接访问业务数据库或观测基础设施。
- 实现默认确定性诊断与可选 OpenAI-compatible Tool Calling 双模式，约束模型步数、
  工具总数、证据覆盖和结构化输出，贯通模型/Prompt/Token 审计，并在模型失败时显式
  标记 `LLM_FALLBACK`；真实供应商调用仍作为可选验收项。
- 使用 `BAAI/bge-small-zh-v1.5`、Chroma、BM25 和 RRF 构建 9 份 Runbook 的混合
  检索；24 条中英文回归查询 Hit@1/Hit@3/MRR 均为 1.00，三类故障整栈诊断
  `3/3 PASS`，并接入 Resilience4j、Prometheus、Grafana、OpenTelemetry、Tempo、
  GitHub Actions 和 10 服务 Docker Compose。

不要把最后一条改写成“RAG 准确率 100%”。正确含义是固定、人工策划的 24 条回归
查询全部首位命中。

## 一段话版

设计并实现 OpsMind AI 微服务故障诊断平台，以 Spring Boot 作为业务控制面，负责

## 60 秒开场

OpsMind AI 是一个面向模拟微服务故障的证据驱动诊断平台。它不是普通 RAG 聊天页，
重点是把 AI 放进一条真实的后端工程链路。

故障发生后，Spring Boot 立即创建异步任务并返回 `taskId`，诊断过程通过 SSE 推送。
Python Agent 只能通过 Spring Tool Gateway 查询日志、指标、Trace、发布记录和
Runbook，所有调用都会审计。默认确定性模式保证面试现场无密钥也能稳定演示；可选
LLM 模式兼容 Chat Completions Tool Calling，并在代码层限制工具、服务、Trace、步数
和最终 JSON 合同。报告、模型元数据和跨服务 Trace 都会落库或进入可观测系统。

我还为检索和完整诊断分别做了自动评测，因此项目不仅能跑，也能解释质量如何被验证。

## 五分钟讲解顺序

1. 先讲问题：AI 诊断慢、易失败、需要访问敏感工具，也容易生成无证据结论。
2. 讲 Java 控制面：异步任务、数据库事实、Redis 加速、SSE 通知和 Resilience4j。
3. 讲工具边界：Python 不碰业务库，所有能力经 Tool Gateway、归属校验和审计。
4. 讲双模式：确定性基线保证复现，LLM 模式展示真实工具协议和显式 fallback。
5. 讲 RAG：Dense 解决语义，BM25 解决运维关键词，RRF 解决分值尺度差异。
6. 讲证据：3/3 整栈场景、24 条 RAG 回归、16 Java、24 Python、浏览器双视口。
7. 最后讲边界：数据源是模拟的，真实模型尚需供应商验收，生产还需 RBAC 和审批。

## 技术亮点

- 数据库先保存、Redis 再更新、SSE 最后推送，断线后仍能恢复可靠状态。
- SSE 订阅先发送当前快照，避免快速任务在浏览器建连前已结束而丢失终态。
- Tool Gateway 是模型与业务系统之间的能力边界，不只是一个 HTTP 转发层。
- LLM 模式只开放五个只读工具；事故复盘仍是用户触发的后端命令。
- 模型参数在代码层收敛到当前 Incident，Prompt 不是唯一安全措施。
- `executionMode` 区分 `DETERMINISTIC/LLM/LLM_FALLBACK`，避免审计语义混乱。
- 模型名和 Prompt 版本进入数据库审计，不进入 Prometheus 标签，防止高基数。
- 混合检索结果保留 Dense/BM25 排名和 RRF 分数，便于解释召回来源。
- 诊断评测和 RAG 排名评测分开，避免用“最终回答看起来对”代替检索测量。
- CI、Compose smoke 和 Playwright 验收分别覆盖代码、运行时与视觉交付风险。

## 高频问题

### 为什么后端是 Spring Boot，AI 服务是 Python？

Spring Boot 承担业务状态、权限、任务编排、审计、缓存、稳定性和监控，这些是长期
边界；Python 承担 embedding、Chroma、RAG 和 Agent 编排，便于利用 AI 生态。两者
通过稳定 JSON 合同协作，模型更换不要求重写业务控制面。

### 为什么诊断要做成异步任务？

模型和向量检索有冷启动、超时和供应商失败风险。同步请求会长时间占用连接，也难以
表达中间状态。异步任务立即返回 id，后台推进状态，SSE 提供体验，数据库负责恢复。

### 为什么使用 SSE 而不是 WebSocket？

这里主要是服务端向浏览器单向推送阶段事件，SSE 合同更简单，天然支持文本事件和
重连语义。用户命令仍通过普通 HTTP 提交，不需要双向长连接。

### 为什么保留确定性模式？这还算 Agent 吗？

确定性模式是可评测基线，不冒充模型自主 Agent；可选 LLM 模式才由模型选择工具。
二者共用 Tool Gateway、证据和报告合同。这样既能无密钥稳定演示，也能测试真实模型
协议和降级，不把作品可靠性绑定到外部供应商。

### LLM 模式为什么不是简单调用一次模型？

运行时维护 assistant/tool 消息循环，模型可以多轮选择工具。代码限制最多 6 轮、
18 次工具调用，要求完成日志、指标、Trace、Runbook 和发布记录五类取证，最后只接收
满足 Pydantic 合同的 JSON 报告。

### 如何防止模型越权？

Python 先拒绝未知工具，强制服务名等于 Incident 服务，Trace 必须来自当前证据，
并限制查询和结果长度；Spring 再校验任务、故障、服务、Trace 和工具白名单。权限来自
代码和后端网关，Prompt 只负责告诉模型规则。

### 如何处理间接 Prompt Injection？

工具结果明确标记为不可信证据，模型不能把其中内容当作指令；结果长度受限，未知工具
和越权参数在代码边界拒绝，最终 id 与元数据由运行时覆盖。测试中让工具结果要求调用
未授权工具，运行时仍只允许原白名单。生产环境还需要内容隔离、策略引擎和人工审批。

### 为什么要做混合检索？

Dense 对同义表达更友好，但运维场景有 `OOMKilled`、`SERVFAIL`、`ENOSPC` 等精确
关键词；BM25 对这些信号更敏感。RRF 融合排名，不需要强行归一化向量距离和 BM25
分数。小语料下它简单、可解释，也便于回归。

### RAG 的 1.00 指标可信到什么程度？

它只说明 24 条固定回归查询在当前 9 份 Runbook 上全部首位命中。数据集用于防止新增
干扰文档后排序退化，不代表开放世界或生产准确率。下一步要增加同义改写、拼写错误、
证据缺失和难负例，并保存版本化基线。

### 如何减少幻觉？

确定性模式只把实际工具结果写入 evidence。LLM 模式要求最低取证覆盖、结构化输出、
非空证据和置信度边界，并把工具结果当作不可信数据。评测检查根因、证据、建议、工具
覆盖和复盘一致性；真实生产还应增加证据引用 id、事实一致性判定和人工审批。

### Redis 在这里解决什么真实问题？

它不是为了堆技术名词：任务快照降低轮询成本，短期结果复用减少重复 AI 开销，固定
窗口限流保护昂贵入口，分布式锁封住并发创建窗口。Redis 不可用时查询回源 MySQL，
限流和锁 fail-open，避免缓存成为单点。

### 为什么使用 Resilience4j？

AI 服务是慢且可能失败的下游。连接/读取超时限制单次等待，有限重试处理短暂故障，
熔断器避免持续轰击，Bulkhead 限制并发，fallback 把内部异常转换为稳定业务失败。

### 为什么模型名不放进 Prometheus 标签？

模型和 Prompt 版本可能频繁变化，甚至来自配置。作为标签会产生高基数和长期时序成本。
Prometheus 只按固定执行模式统计，详细模型版本进入可查询的数据库审计。

### 为什么确定性报告里的 `toolCallCount` 是 0？

这个字段只统计模型主动发起的工具调用，用于衡量 Agent 循环。确定性工作流的真实工具
调用仍完整保存在 ToolCallAudit 中。把两个计数混在一起会误导成本和行为分析。

### 是否需要多 Agent？

当前不需要。一次诊断围绕同一个 Incident、同一套只读取证工具和一个报告合同，单
Agent 更容易控制权限、成本和评测。开发阶段使用主/子 Agent 并行写 CI、RAG 和
Runbook，但那是研发协作方式，不是产品运行时能力。

### 项目是不是生产级？

不是，准确定位是作品级和学习型平台。它证明了 AI 应用落地的关键工程问题，但观测
数据仍是模拟的，真实生产还需要告警/日志平台适配、身份与租户、RBAC、脱敏、审批、
灾备和 SLO。主动说明边界比把项目包装成生产系统更可信。

## 复盘问题

### 本轮最有价值的工程问题是什么？

不是某个算法，而是 Docker 冷构建。原 Dockerfile 把依赖只放在 BuildKit cache mount
中，依赖预取层可能命中但缓存卷已经为空，导致后续 package 长时间联网失败。最终改为
实际 `package` 产出 JAR 层，仓库 mount 只负责加速；这样层缓存命中时 JAR 一定存在，
缓存丢失时也只是重新下载，不会产生错误成功状态。

### 如果再做一次，开发顺序如何调整？

先冻结请求/报告/审计合同和验收数据，再实现确定性基线；随后做 Tool Gateway 权限，
再接模型循环；RAG 必须从第一天带干扰文档和排名评测；最后才更新简历。这样能减少
接口反复和“代码已经变了、文档仍停在旧边界”的漂移。

## 现场演示话术

演示默认使用确定性模式：

1. 说明它是无密钥可复现基线，不冒充真实模型。
2. 注入一个故障并启动诊断，强调接口立即返回任务。
3. 展示 SSE、六类工具审计和报告中的来源证据。
4. 展示执行模式、模型/Prompt 元数据和 TraceId。
5. 打开 Grafana/Tempo，再展示评测报告。
6. 最后打开 LLM 配置文档和单测，说明接真实供应商还差哪一步验收。
