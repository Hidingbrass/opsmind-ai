# 简历与面试材料

## 简历描述版本 1

设计并实现 OpsMind AI 智能故障诊断平台，面向微服务系统提供证据驱动的故障分析能力。系统以 Spring Boot 作为后端控制面，支持故障事件管理、异步诊断任务、SSE 实时推送、诊断工具网关、Redis 缓存限流、Resilience4j 熔断降级和审计落库；以 Python 服务实现 Runbook RAG、多工具取证和结构化根因报告生成。

## 简历描述版本 2

构建面向微服务故障诊断的 AI Agent 平台，基于 Spring Boot 设计诊断任务编排和 Tool Gateway，基于 Chroma 与中文 embedding 实现 Runbook RAG，统一执行日志、指标、链路追踪、发布记录和复盘工具；使用 Redis 完成任务状态缓存、结果复用、请求限流和重复任务去重，并通过 SSE 将诊断过程实时推送到前端。

## 简历描述版本 3

实现一个具备工程化能力的 AI SRE 故障诊断系统：通过异步任务解耦耗时诊断，通过 Tool Gateway 控制 Python 工具访问权限，通过审计表记录工具调用、AI 服务调用和诊断报告，通过 Resilience4j 提供超时、重试、熔断和并发隔离，并接入 Prometheus、Grafana、OpenTelemetry 与 Tempo 观测诊断成功率、调用延迟和跨服务 TraceId。

## 面试讲解开场

OpsMind AI 是一个面向模拟微服务故障的 AI SRE 平台。它的核心不是做一个普通聊天机器人，而是让 AI 能够在后端系统的约束下调用工具、检索知识、生成带证据的诊断报告。

当故障发生时，Spring Boot 后端会创建故障事件和异步诊断任务，Python 诊断工作流会通过 Tool Gateway 查询日志、指标、链路追踪、最近发布记录，并从 Chroma 运维知识库检索相关 Runbook，最后生成根因分析、修复建议和事故复盘。诊断过程通过 SSE 推送到前端，工具调用和 Python 服务调用会审计落库，Redis 用于缓存、限流和任务状态管理。

这个项目的重点是把 AI 能力放进真实后端工程链路中，而不是只展示一次模型调用。

## 技术亮点

- 使用 Spring Boot 作为业务后端、诊断任务编排器和工具执行网关。
- 使用异步任务模型处理耗时 AI 诊断，避免 HTTP 请求长时间阻塞。
- 使用 SSE 将诊断任务状态和 Agent 工具调用过程实时推送到前端。
- 使用 Chroma 存储运维手册和历史故障案例，实现 Runbook RAG 检索。
- 使用确定性多工具工作流调用日志、指标、链路、Runbook 和发布记录，所有调用经过 Tool Gateway。
- 使用 Redis 实现诊断结果缓存、请求限流、任务状态管理和重复任务去重。
- 使用 HTTP 超时与 Resilience4j 实现 AI 服务调用的重试、熔断、并发隔离和 fallback。
- 使用审计表记录工具调用、Python AI 服务调用、诊断报告和关键耗时。
- 使用 Prometheus、Grafana 和 OpenTelemetry 观测任务成功率、调用延迟和 TraceId 链路。
- 使用 AI 诊断评测集评估根因命中、证据引用、修复建议质量和幻觉风险。

## 需要准备回答的问题

### 为什么后端是 Spring Boot，AI 服务是 Python？

Spring Boot 更适合承载业务状态、权限边界、任务编排、审计、缓存、限流和系统稳定性；Python 生态更适合向量模型、Chroma、RAG 和评测工具。两者拆开后，Java 后端控制业务和工程边界，Python 服务专注证据取回与诊断编排。

### 为什么 AI 诊断要做成异步任务？

AI 调用通常耗时长、失败率高、成本也更高。如果让 HTTP 请求一直阻塞，用户体验和系统稳定性都不好。异步任务可以立即返回 `taskId`，后台执行诊断，前端通过查询或 SSE 获取进度，同时方便记录失败原因、重试次数和任务审计。

### 为什么要用 SSE？

AI 诊断过程天然是单向流式输出：查询日志、查询指标、检索 Runbook、调用工具、生成报告。SSE 比 WebSocket 更简单，适合服务端持续向前端推送任务进度和模型输出。

### 为什么这里要用 RAG？

故障诊断依赖公司内部的运维手册、历史故障案例和服务知识，这些内容通常不在大模型训练数据中。RAG 可以让 Agent 基于可检索的运维知识进行回答，而不是凭空生成。

### 为什么要做工具调用？

诊断不能只接收一大段静态文本。工作流需要主动查询日志、指标、Trace、发布记录和 Runbook。受控工具调用让取证过程可观察、可控制、可追踪，也为以后接入模型自主工具选择保留了边界。

### 为什么工具调用要经过后端 Tool Gateway？

Python 服务和未来接入的模型都不能直接访问业务数据库或基础设施。Tool Gateway 可以统一做权限控制、入参校验、结果脱敏、错误处理和审计落库，让工具调用变成可控的后端能力。

### 为什么要用 Redis？

Redis 可以用于重复诊断结果缓存、请求限流、诊断任务进度存储和重复任务去重，也可以扩展为 Redis Stream 事件队列。AI 应用中大模型调用通常慢且成本高，所以缓存、限流和任务状态管理很有价值。

### 为什么要用 Resilience4j？

AI 服务和向量数据库都可能慢、失败或不可用，未来接入模型供应商后风险还会增加。Resilience4j 可以为下游调用提供超时、重试、熔断、并发隔离和降级，避免某个下游异常拖垮主后端。

### 如何减少模型幻觉？

当前确定性诊断器只把真实命中的日志、指标、链路、发布记录或 Runbook 写入 evidence，不从缺失数据中编造证据；三场景评测会检查根因、证据、建议、工具覆盖和复盘一致性。接入生成式模型后也必须继续遵守这个证据合同。

### 这个项目和普通 RAG 问答有什么区别？

普通 RAG 问答主要是检索文档后回答问题。OpsMind AI 的 RAG 是诊断链路的一部分，工作流还会调用日志、指标、链路追踪和发布记录工具，并且所有工具调用都由后端审计和控制，最终输出结构化诊断报告。

### 为什么默认不用外部生成式大模型？

作品演示需要离线可复现、无需 API Key，并且三种固定场景要能自动评测。因此默认使用确定性多工具诊断和中文 embedding RAG。外部 LLM 是可插拔增强项，不应在没有真实接入和验收前写进简历。

### 如果面试官问项目是不是生产级系统，怎么回答？

可以回答：这个项目是作品级和学习型平台，不宣称替代真实生产 SRE 系统。它重点展示 AI 应用落地中的关键工程问题：任务编排、工具调用、RAG、缓存限流、审计、熔断、可观测性和评测。真实生产还需要更严格的权限、数据安全、多租户、告警接入和运维流程审批。
