# 简历与面试材料

## 简历描述版本 1

设计并实现 OpsMind AI 智能故障诊断平台，面向微服务系统提供 AI 驱动的故障分析能力。系统集成 Spring Boot、LangChain、Chroma、Redis 和 Nginx，支持故障事件管理、可观测性数据分析、运维手册 RAG 检索、Function Calling 诊断工具调用、根因分析、修复建议生成和事故复盘报告生成。

## 简历描述版本 2

构建面向微服务故障诊断的 AI Agent 平台，基于 Chroma 实现运维手册和历史故障案例的 RAG 检索，基于 Function Calling 实现日志、指标、链路追踪和发布记录查询工具调用，使用 Redis 完成诊断结果缓存、任务状态管理和请求限流，并通过 SSE 实现 AI 诊断过程实时流式输出。

## 面试讲解开场

OpsMind AI 是一个面向模拟微服务故障的 AI SRE 助手。它的核心不是做一个普通聊天机器人，而是让 AI 能够和系统工具交互。当故障发生时，Agent 会查询日志、指标、链路追踪、最近发布记录，并从 Chroma 运维知识库中检索相关 Runbook，最后生成带证据的根因分析和修复方案。

这个项目的定位是一个真实感较强的 AI 应用项目，而不是生产级 SRE 平台。我重点关注的是如何把 RAG、Function Calling、Redis、Spring Boot 和部署基础设施组合成一个完整的工程闭环。

## 技术亮点

- 使用 Spring Boot 作为主后端和工具执行网关。
- 使用 Chroma 存储运维手册和历史故障案例。
- 使用 Redis 实现结果缓存、请求限流和诊断任务状态存储。
- 使用 Function Calling 让模型自主选择诊断工具。
- 使用 SSE 将诊断过程流式推送到前端。
- 使用 Nginx 和 Docker Compose 本地运行完整系统。

## 需要准备回答的问题

### 为什么这里要用 RAG？

因为故障诊断依赖公司内部的运维手册、历史故障案例和服务知识，这些内容通常不在大模型训练数据中。RAG 可以让 Agent 基于可检索的运维知识进行回答，而不是凭空生成。

### 为什么要用 Redis？

Redis 可以用于重复诊断结果缓存、请求限流、诊断任务进度存储，也可以扩展为异步事件队列。AI 应用中大模型调用通常慢且成本高，所以缓存和任务状态管理很有价值。

### 为什么要用 Function Calling？

模型不应该只生成文字。它应该能判断什么时候查询日志、什么时候查询指标、什么时候检索运维手册。Function Calling 可以让诊断流程变得可观察、可控制、可追踪。

### 如何减少模型幻觉？

诊断 Prompt 会要求模型必须提供证据。最终报告必须引用日志、指标异常、链路节点或运维手册片段。如果证据不足，Agent 应该明确说明无法确定根因，而不是编造答案。
