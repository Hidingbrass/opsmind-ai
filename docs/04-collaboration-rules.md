# 协作规则

这份文档用于约束 OpsMind AI 项目的后续开发节奏，确保每一步都能被理解、复盘和写进简历。

## 核心原则

后续开发默认采用“先讲清楚，再决定是否动手”的方式。

除非用户明确说“直接完成”“你来做”“开始写代码”“提交”，否则不要直接修改业务代码。

## 每一步开始前必须说明

在进入一个新功能或新模块之前，必须先解释四件事：

1. 这一步要做什么。
2. 为什么现在要做这一步。
3. 这样做对项目有什么好处。
4. 用户需要理解哪些关键概念。

说明要尽量贴近当前项目，不讲空泛概念。

## 推荐讲解格式

每个新任务先按下面格式说明：

```text
本步目标：

我们要做什么：

为什么要这样做：

这样做的好处：

涉及的文件或目录：

完成后的验证方式：

你需要理解的重点：
```

如果用户确认继续，再开始创建或修改代码。

## 实现前的确认规则

以下情况必须先等用户确认，不能直接动手：

- 新增一个业务模块。
- 改动包结构。
- 引入新的技术组件或依赖。
- 修改数据库表结构。
- 修改 Docker、Nginx、部署配置。
- 做较大范围重构。
- 提交 Git commit。

以下情况可以直接做：

- 用户明确要求创建文档、修改文档或提交。
- 用户明确说“直接完成”。
- 修复刚刚由当前步骤引入的小错误。
- 查看文件、查看 Git 状态、运行只读命令。

## 编码后的说明规则

每次代码改完后，必须说明：

1. 修改了哪些文件。
2. 每个文件承担什么职责。
3. 新增或修改了哪些接口。
4. 如何验证。
5. 是否已经提交。

## 提交规则

每次提交前必须：

- 查看 `git status --short`。
- 确认没有无关文件。
- 运行与本次改动相关的验证命令。

提交信息使用中文，描述要具体，例如：

```text
添加故障事件基础业务模块
规范化后端模块包结构
添加 Docker Compose 基础设施服务
```

## 学习目标

这个项目不是只追求功能堆砌，而是让用户理解：

- 为什么需要这个模块。
- 它在真实业务系统中解决什么问题。
- 它如何和其他模块协作。
- 它在简历和面试中应该怎么讲。

因此，每一步都应该服务于“能做出来、能讲清楚、能被面试追问”的目标。
