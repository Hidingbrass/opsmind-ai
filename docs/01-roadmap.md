# 开发路线图

这份路线图描述 OpsMind AI 从可运行 MVP 到作品级项目的交付路径。详细执行步骤见 `docs/05-execution-plan.md`。

## 总体时间

```text
每天 2-3 小时：5-8 周完成作品级版本。
每天 4-5 小时：3-5 周完成作品级版本。
每天 6 小时以上：2-3 周完成作品级版本。
```

项目分为三层：

```text
MVP 版本：完成故障诊断闭环。
增强版本：补齐后端工程化和 Agent 过程可观测。
冲刺版本：补齐监控、评测、部署和面试材料。
```

## MVP 版本

目标：先做出能演示的完整闭环。

预计时间：2-3 周。

### 第 1 阶段：项目骨架和基础设施

状态：已基本完成。

交付物：

- Spring Boot 后端骨架。
- Python AI 服务骨架。
- Redis、MySQL、Chroma 基础设施。
- Docker Compose 基础配置。
- 健康检查接口。

验收标准：

- `GET /api/health` 返回后端健康状态。
- `GET /ai/health` 返回 AI 服务健康状态。
- Redis、MySQL、Chroma 可以本地启动。

### 第 2 阶段：故障事件和故障注入

状态：当前推进中。

预计时间：2-3 天。

交付物：

- 故障事件实体和 API。
- 故障状态：待处理、诊断中、已解决。
- 故障场景模型。
- 模拟故障注入接口。
- 支付超时、Redis 异常、数据库慢查询三个基础场景。

验收标准：

- 用户可以创建一条支付服务超时故障。
- 用户可以查询故障详情。
- 用户可以通过场景接口一键注入故障。

### 第 3 阶段：模拟可观测性数据

预计时间：2-3 天。

交付物：

- 日志查询接口。
- 指标查询接口。
- 链路追踪查询接口。
- 每个故障场景对应的静态日志、指标和链路数据。
- `traceId` 和 `incidentId` 关联。

验收标准：

- 注入故障后，后端可以返回相关日志、指标和链路数据。
- 数据可以支撑一份带证据的诊断报告。

### 第 4 阶段：基础 AI 诊断

预计时间：3-4 天。

交付物：

- AI 诊断 Prompt。
- Spring Boot 调用 Python AI 服务。
- 结构化诊断报告 DTO。
- 诊断报告持久化。

验收标准：

- 用户点击“开始诊断”。
- 系统生成根因、证据和修复建议。
- 诊断报告能被查询和复用。

### 第 5 阶段：Runbook RAG 知识库

预计时间：3-5 天。

交付物：

- 运维手册文档格式。
- 文档导入脚本。
- 文本切分。
- Chroma 向量存储。
- Runbook 检索 API。
- 报告证据引用。

验收标准：

- 可以导入支付服务超时运维手册。
- AI 诊断会使用检索到的运维手册内容。
- 最终报告包含引用来源。

## 增强版本

目标：让项目从 AI Demo 升级为有工程质感的后端平台。

预计时间：2-3 周。

### 第 6 阶段：异步诊断任务

预计时间：3-4 天。

交付物：

- `DiagnosisTask` 模型。
- 任务状态机。
- 创建任务接口。
- 查询任务接口。
- 后台执行诊断。
- 成功诊断记录 id。
- 失败原因记录。

验收标准：

- 创建诊断任务后立即返回 `taskId`。
- 用户可以查询任务状态。
- 任务成功后可以查询到 `diagnosisRecordId`。
- AI 服务异常时任务状态明确失败。

### 第 7 阶段：SSE 诊断过程推送

预计时间：2-3 天。

状态：后端 SSE 闭环已完成，前端诊断时间线留到控制台阶段实现。

交付物：

- SSE 订阅接口。
- 诊断事件模型。
- 任务阶段事件。
- 前端诊断时间线。

验收标准：

- SSE 订阅接口能推送当前任务快照和后续过程事件。
- `SUCCESS` 事件包含 `diagnosisRecordId`，`FAILED` 事件包含 `failureReason`。
- 终态事件与数据库记录一致，推送后连接自动关闭。
- 控制台阶段将这些事件展示为诊断时间线。

### 第 8 阶段：Function Calling 和工具网关

预计时间：4-6 天。

状态：`queryLogs` 工具执行与结构化成功/失败返回已完成，Python Agent 主动调用和其余只读工具待补。

交付物：

- 工具定义。
- Tool Gateway。
- 工具调用执行器。
- 工具调用入参校验。
- 工具调用结果摘要。
- 危险操作人工确认机制。

验收标准：

- Agent 能调用日志、指标、链路、Runbook 和发布记录工具。
- 前端能展示每一次工具调用。
- 工具失败时系统能给出清晰错误。

### 第 9 阶段：诊断审计和 Redis 工程化

预计时间：3-5 天。

状态：工具调用审计实体、Repository 和写入 Service 已完成，并已验证成功与失败记录真实落库；审计查询接口和 Redis 工程化待补。

交付物：

- 工具调用审计表。
- 模型调用记录。
- 诊断结果缓存。
- 请求限流。
- 任务状态缓存。
- 重复任务去重。
- 可选 Redis Stream 事件流。

验收标准：

- 重复诊断同一故障时可以命中缓存。
- 过于频繁的诊断请求会被友好拒绝。
- 页面刷新后仍能恢复诊断任务状态。
- 每次工具调用都有可查询的审计记录。

### 第 10 阶段：Resilience4j 稳定性保护

预计时间：2-4 天。

交付物：

- AI 服务调用超时。
- 失败重试。
- 熔断降级。
- 接口限流。
- fallback 返回。

验收标准：

- AI 服务停止时后端不会长时间卡死。
- 连续失败后触发熔断。
- 熔断期间返回明确的降级信息。

## 冲刺版本

目标：让项目具备作品集展示质量和更强面试表达。

预计时间：1-2 周。

### 第 11 阶段：Prometheus、Grafana 和 OpenTelemetry

预计时间：3-5 天。

交付物：

- Spring Boot Actuator。
- Micrometer Prometheus 指标。
- Prometheus 配置。
- Grafana Dashboard。
- OpenTelemetry TraceId 串联。

验收标准：

- `/actuator/prometheus` 可以暴露指标。
- Grafana 能看到任务成功率、失败率、接口耗时、AI 调用延迟。
- 日志、诊断任务和工具调用记录可以通过 `traceId` 关联。

### 第 12 阶段：AI 诊断质量评测

预计时间：2-4 天。

交付物：

- 固定故障评测集。
- 期望根因和关键证据。
- 自动评测脚本。
- 评测报告。
- 模型调用成本和延迟统计。

验收标准：

- 可以一键运行多个故障场景的诊断评测。
- 报告能展示根因命中、证据引用、修复建议质量和幻觉风险。

### 第 13 阶段：控制台和演示打磨

预计时间：4-7 天。

交付物：

- 故障控制台。
- 故障注入面板。
- 诊断任务详情。
- 诊断时间线。
- 工具调用详情。
- 报告页面。
- 架构图。

验收标准：

- 招聘方或面试官可以在 3 分钟内理解项目价值。
- 技术面试官可以围绕后端架构、Redis、异步任务、RAG 和 Function Calling 继续追问。

### 第 14 阶段：部署和简历材料

预计时间：3-5 天。

交付物：

- 后端 Dockerfile。
- AI 服务 Dockerfile。
- 前端构建。
- Nginx 反向代理。
- Docker Compose 完整编排。
- API 文档。
- README 完整化。
- 简历项目描述。
- 面试讲解脚本。

验收标准：

- 新机器拉取代码后，可以按照文档在本地启动。
- README 能解释架构、演示步骤和技术亮点。
- 简历描述能突出 Java 后端工程能力和 AI 应用落地能力。

## 阶段自查清单

每个阶段结束前，都要回到 `docs/05-execution-plan.md` 的“项目盲点与防翻车清单”做一次自查，重点确认：

- 范围是否失控，是否影响核心闭环。
- 日志、指标、链路、Runbook 是否能形成证据链。
- AI 输出是否是结构化报告，而不是自由文本。
- Java 后端和 Python AI 服务边界是否清晰。
- 当前阶段是否有 curl、页面、数据库或日志层面的验收证据。
- 工具调用是否经过后端网关、审计和权限控制。
- 前端是否能展示诊断过程、工具调用和证据来源。
- 简历表达是否和真实实现保持一致。
